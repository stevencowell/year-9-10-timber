# Year 9-10 Timber remediation and release plan

Status: approved for implementation by Steve on 1 August 2026.

## Purpose

Bring the shared Timber hub, its curriculum evidence maps and the seven linked project sites into a defensible, maintainable state. The work must distinguish published webpage evidence, teacher-observed workshop evidence and formal program coverage.

## Source hierarchy

1. Current and future syllabus statements recorded in the two supplied program documents.
2. Verified project drawings, assessment material, folios and local workshop procedures.
3. The live project webpages and their active student evidence.
4. Sister-site interaction and visual patterns.

No project dimensions, assessment dates, weightings, local procedures or syllabus claims will be invented.

## Repair decisions

### 1. Correct the current audit

- Retain `I = introduced`, `P = practised and developed`, and `E = evidenced or assessed`.
- Use Australian English. `Practised` is the correct verb; `practice` remains the correct noun.
- Correct Clock IND5-9 to reflect its live Weeks 15-16 technology comparison and saved written response.
- Distinguish webpage-captured evidence from teacher observation. A practical collaboration outcome is not automatically a website gap when it is intentionally verified by the teacher.
- Recheck every current-outcome reference after the source-site repairs.

### 2. Repair live-site anomalies

- Mirror: replace the 20 broken `weeks/main/` links with the existing verified week-support routes and test all 20 destinations.
- Remove or qualify unsupported landing-page outcome claims. A landing-page list alone will not be treated as evidence.
- Add only source-backed student evidence where a real syllabus/program requirement is otherwise missing.
- Preserve the existing project plans, approved imagery, layout and completed learning content.

### 3. Create the two missing programs

- Create a Small Box program using its verified three-module sequence and only future-syllabus statements supported by the supplied program document.
- Create a Folding Chair program using its verified ten-module sequence, plans and active evidence.
- Label both as local school program additions. They were not named in the supplied 2025 master Timber program, so the new documents must not imply that they were part of that original source.
- Include outcome mapping, learning sequence, active evidence, teacher-observation requirements, resources and unresolved local decisions. Do not add dates or weightings.

### 4. Build a separate new-syllabus audit

- Create `Timber Course New Syllabus Alignment Audit.xlsx` as a separate workbook.
- Use the exact future-syllabus content statements recorded in the supplied future program as matrix rows.
- Map the seven-project sequence with I/P/E and precise webpage, module or program references.
- Keep unsupported cells blank with a reason. Do not infer authoritative outcome descriptions beyond the supplied source.
- Include Overview and Legend, Content Alignment Matrix, Project Evidence, Program Coverage and Source Register sheets.

### 5. Update the shared landing page

- Add clear download cards for the current-syllabus audit and the new-syllabus audit.
- Add the Small Box and Folding Chair program downloads in the correct current/future resource context.
- Keep existing project text, order, approved Clock/Mirror images and verified Drive links unchanged unless a source correction requires otherwise.

### 6. Quality and release gates

- Validate all local links and assets, with no missing intended routes.
- Test the landing page at desktop and mobile widths in the in-app browser.
- Reopen both exported Excel workbooks, inspect key ranges, scan for formula errors and render every sheet.
- Render and inspect every page of both new Word programs.
- Commit and push only the intended current repositories. Preserve legacy repositories and the dirty older Small Box checkout.
- Create or confirm the dedicated hub repository, enable GitHub Pages, reload the live page and verify both workbook downloads before reporting release.

## Completion evidence

The work is complete only when the two audits and two program documents are present in the published hub, the repaired project routes return the intended content, the GitHub Pages landing page renders correctly at desktop and mobile widths, and each published download has been opened or fetched successfully from the live site.
